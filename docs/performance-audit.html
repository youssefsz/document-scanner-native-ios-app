Document performance, measured.

A focused update to the document viewer and PDF pipeline, measured on a real iPhone with disposable test documents.

16 September 2026iPhone 15 · iOS 27.0Branch: feat/document-hero-performance
01 / measured result

Lower average peak, with overlapping runs

52.7 MB before→50.3 MB after4.6% lower mean

Peak physical memory from XCTest while the same generated 20-page PDF stayed open for 30 seconds. Two runs per version; decimal MB.

The old runs measured 56.5 and 48.8 MB; the updated runs measured 47.1 and 53.4 MB. The ranges overlap, so this small sample does not establish a reliable whole-app memory gain. The old build came from the branch's committed starting point in a temporary source archive. All runs used the same separately installed test app and document fixture.

03 / implementation

Changes made

Viewer

The first page can use its existing library thumbnail during the hero transition. A page session opens the PDF once, renders requested pages off the main actor, and keeps only nearby page views and snapshots. A memory warning drops noncurrent cached pages.

Scan and OCR

The PDF writer accepts one page at a time. Scan saving and legacy searchable-PDF conversion now pass each page through OCR and writing in sequence, avoiding an array of every rendered page.

Share and export

Quality previews cancel obsolete work, share can reuse the selected prepared file, and each export gets its own temporary directory. Failed or canceled exports remove partial files; file size comes from the file system without reading the whole PDF into memory.

Output quality

PDF pages now rasterize to the selected target dimension. A regression test checks 1,280- and 2,240-pixel outputs from a standard PDF page, preventing a low-resolution export caused by the former one-times scale cap.

04 / verification

What was exercised

Passed on iPhone

Document pipeline

Generated 100-page and 20-page PDFs; checked page-on-demand rendering, searchable text after scan saving and every export quality, actual file sizes, high and very-high exports of the 20-page photo PDF, and canceled export cleanup.

6 of 6 UI tests passed

Viewer interactions

The library and ordinary-folder hero transitions, 100-page opening, scrolling and reopening, 20-page share setup, and both viewer memory scenarios passed on the iPhone. A system sign-in alert interrupted the first full run; the test harness canceled it and the rerun passed.

62 of 62 unit tests passed

Regression suite

The final complete unit run passed on the iPhone. An earlier run had two intermittent ProStore lifecycle timeouts; both passed on rerun, and one also failed on the untouched baseline. The exact timing trigger remains unconfirmed.

Scope

What this does not prove

The camera was not exercised. Secure viewing still uses a Data-backed PDF after protected temporary decryption, and its peak was not benchmarked here. OCR accuracy across languages, extreme page counts and long-running field use need larger data sets. Two memory iterations per version cannot establish a stable device-wide effect.

05 / method and references

How to read the numbers

The test app uses bundle ID tn.document-scaner.performance, separate from the personal app. It generated 150 archive entries plus 100-page, 20-page and one-page PDFs in its own container. XCTMemoryMetric(application:) sampled the test app while the 20-page document was visible. The report uses its peak physical memory value.

Apple recommends measuring a specific feature, reducing oversized image work, and guarding against memory regressions. The page-window and sequential PDF writer are engineering choices informed by that guidance; Apple does not prescribe these exact cache counts or sizes.
